## Целевая структура

```text
backend/    Java API, бизнес-логика, миграции и тесты
frontend/   React, страницы, компоненты и UI-тесты
infra/      конфигурация контейнеров и исходного развёртывания
scripts/    команды локального запуска и сборки
docs/       требования, архитектура, проверки и инструкции
.github/    GitHub Actions и шаблон Pull Request
```

Каталоги создаются по мере переноса соответствующего модуля. Начальный коммит содержит документацию и общие настройки. Каркас React содержит главную страницу, раздел «О сервисе», маршрутизацию и адаптивное оформление, а функциональные страницы и API будут добавляться отдельно.

## Архитектурные решения

Приложение переносится как единый репозиторий с frontend, backend и конфигурацией запуска. React собирается в статические ресурсы общего Spring Boot JAR. PostgreSQL хранит данные; изменения схемы выполняются через Flyway в порядке V1–V4. Время мероприятий хранится с однозначной временной привязкой, а интерфейс кампуса использует Europe/Moscow.

Для входа применяются серверная сессия, BCrypt и CSRF-защита. Сервер проверяет роли и владельца мероприятия независимо от доступности кнопок в интерфейсе. Изображения хранятся в отдельной таблице PostgreSQL. Проверки и сборка на GitHub настраиваются отдельно от исходного GitLab CI.

## Условия завершения переноса

- Код собирается из чистой рабочей копии по актуальной инструкции.
- Миграции применяются к новой базе и не теряют данные при повторном запуске.
- Реализованные сценарии афиши, авторизации, ролей, управления событиями, модерации и фото проходят проверки.
- GitHub CI запускается для Pull Request; результаты проверок доступны для просмотра.
- Фактические ручные прогоны и открытые дефекты записаны в протокол, а старые результаты GitLab не выдаются за новые.
- Различия между исходным и перенесённым кодом объяснены; происхождение исходных функций сохранено.
- Другой участник команды воспроизводит запуск по README.

19 ноября прошли чистая установка зависимостей через `npm ci`, ESLint, TypeScript и production-сборка на Node.js 24. В Chrome проверены переходы между страницами, обновление `/about`, неизвестный маршрут и переход к содержимому с клавиатуры. На ширинах 1280 и 360 px нет горизонтального переполнения и ошибок JavaScript; страницы не обращаются к backend. Полные функциональные автотесты добавляются вместе с соответствующими возможностями.

## Следующий этап после переноса

Для полного MVP требуется реализовать запись на мероприятие, защиту от дубликатов, отмену участия, список собственных регистраций и участников события. Эти функции соответствуют ФТ-06–ФТ-09 и ФТ-15 в [требованиях](requirements.md). Сохранность регистраций по ФТ-16 проверяется после появления соответствующей модели.

Сначала необходимо замкнуть сценарий «создание → модерация → публикация → запись студента → участник в кабинете организатора», затем проверить отрицательные случаи, сохранность данных, производительность и обязательные критерии приёмки. Расширение MVP не подменяется дополнительными коммитами уже существующего кода.
