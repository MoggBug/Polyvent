# Публичное API PolEvent

Срез принятого кода — `2841077` от 24 ноября 2026 года. В GitHub сейчас реализованы `/api/info` и сервисные health endpoints. Три маршрута каталога ниже — предлагаемый контракт для этапа 07 по раннему исходнику GitLab; модель V1 этапа 05 ещё не принята. Согласование с Дмитриевым и Беловым ожидается.

Примеры мероприятий и категорий иллюстрируют структуру JSON, а не содержимое работающей базы. Их ID и даты не являются подготовленными тестовыми данными.

## Адреса и состояние маршрутов

Backend по умолчанию доступен на `http://localhost:8080`; порт меняет `APP_PORT`. В разработке Vite принимает `/api` на `http://127.0.0.1:5173` и проксирует их в backend. Текущие страницы React запросов к API ещё не делают.

| Метод и путь | Состояние | Назначение |
| --- | --- | --- |
| `GET /api/info` | Реализован | Название и версия приложения |
| `GET /actuator/health` | Настроен в каркасе | Общее состояние здоровья |
| `GET /actuator/health/readiness` | Настроен в каркасе | Готовность приложения и подключение к PostgreSQL |
| `GET /api/categories` | Предлагаемый, этап 07 | Справочник категорий |
| `GET /api/events` | Предлагаемый, этап 07 | Публичная афиша с фильтрами |
| `GET /api/events/{id}` | Предлагаемый, этап 07 | Публичная карточка опубликованного события |

До переноса 05/07 запрос к маршруту каталога в текущей GitHub-версии возвращает 404. Клиенту не следует считать такой ответ пустой афишей: успешный пустой список имеет HTTP 200 и тело `[]`.

Успешные прикладные ответы — JSON. Списки возвращаются массивом без обёртки, пагинации и общего счётчика. На этапе публичного каталога вход не требуется, а операций изменения данных этот контракт не предоставляет.

## Реализовано — информация о приложении

`GET /api/info` возвращает HTTP 200:

```json
{
  "name": "PolEvent",
  "version": "local"
}
```

`name` — строка `PolEvent`; `version` — строка из `APP_VERSION`, по умолчанию `local`. Это версия сборки, а не версия схемы REST API.

Источник: [InfoController](../backend/src/main/java/ru/ystu/polyvent/common/InfoController.java) и [application.yml](../backend/src/main/resources/application.yml).

## Реализовано — готовность

`GET /actuator/health/readiness` в готовом состоянии возвращает HTTP 200:

```json
{
  "status": "UP"
}
```

В группу включены `readinessState` и `db`. Технические подробности скрыты настройкой `show-details: never`. При неготовности работающего приложения возможен HTTP 503; если запуск завершился ошибкой подключения к БД, HTTP-сервер может вообще не быть доступен. Проверку нельзя заменять одним успешным открытием статической страницы Vite.

Остальные actuator endpoints, например `/actuator/env`, закрыты серверной конфигурацией. Health не предназначен для выдачи строки подключения, паролей или внутренней структуры окружения.

## Предлагаемый контракт — категории

`GET /api/categories`, без параметров. Ожидаемый успешный ответ — HTTP 200 с массивом `CategoryDto`:

```json
[
  {
    "id": 3,
    "slug": "sport",
    "name": "Спорт"
  }
]
```

Показан один пример элемента, а не полный начальный справочник.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | Целое число, Java `Long` | ID категории в БД |
| `slug` | Строка | Значение фильтра `category` |
| `name` | Строка | Подпись для пользователя |

Все поля обязательны. Порядок — по `id` по возрастанию. Начальные slugs V1: `culture`, `science`, `sport`, `community`, `career`, `volunteer`. ID нужно получать из ответа, а не задавать числом в коде клиента. Отсутствие категорий — HTTP 200 с `[]`.

## Предлагаемый контракт — афиша

`GET /api/events` принимает два необязательных query-параметра:

| Параметр | Формат | Правило |
| --- | --- | --- |
| `category` | Строка slug, например `sport` | Равенство `Category.slug`; окружающие пробелы удаляются; регистр не нормализуется |
| `date` | ISO-дата `yyyy-MM-dd`, например `2026-12-05` | Календарные сутки в `Europe/Moscow` |

Если `category` не передан или после удаления пробелов пуст, выбираются все категории. Неизвестный slug даёт пустой результат с HTTP 200. При одновременной передаче фильтры применяются вместе.

Примеры запросов для будущего API:

```text
GET /api/events
GET /api/events?category=sport
GET /api/events?date=2026-12-05
GET /api/events?category=sport&date=2026-12-05
```

Выбираются только `PUBLISHED`. Без `date` нижняя граница — текущий момент сервера; события сортируются по `startsAt`, затем по `id`, по возрастанию. При указанной дате берутся все опубликованные события выбранных московских суток; дополнительного ограничения «позже текущего момента» в этом случае нет.

Для `date=2026-12-05` временные границы:

```text
startsAt >= 2026-12-04T21:00:00Z
startsAt <  2026-12-05T21:00:00Z
```

Успех — HTTP 200 с массивом `EventDto`:

```json
[
  {
    "id": 42,
    "title": "Студенческий турнир",
    "description": "Открытая встреча для студентов кампуса.",
    "location": "Спортивный зал",
    "organizerName": "Студенческое объединение",
    "startsAt": "2026-12-05T15:00:00Z",
    "category": {
      "id": 3,
      "slug": "sport",
      "name": "Спорт"
    }
  }
]
```

Пустой результат — HTTP 200 с `[]`. Сброс фильтров означает удаление обоих параметров и новый запрос `/api/events`.

## Предлагаемый контракт — карточка

`GET /api/events/{id}`, где `id` — числовой идентификатор события типа Java `Long`.

- Существующее `PUBLISHED` — HTTP 200 и один объект `EventDto`, без массива.
- Неизвестный ID либо статус `DRAFT`, `PENDING`, `REJECTED` — HTTP 404.
- Значение, которое нельзя преобразовать в `Long`, например `/api/events/abc`, — HTTP 400.

Проверяется статус публикации, а не время начала: опубликованная карточка прошедшего события остаётся доступной по ID. Клиент не получает внутреннюю причину отсутствия карточки и не должен различать неизвестное событие и закрытый черновик.

## Предлагаемый публичный EventDto

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | Целое число, Java `Long` | ID события |
| `title` | Строка | Название |
| `description` | Строка | Описание |
| `location` | Строка | Место |
| `organizerName` | Строка | Отображаемое имя организатора |
| `startsAt` | ISO-строка с часовым смещением | Момент начала; примеры используют UTC с `Z` |
| `category` | `CategoryDto` | Вложенная категория |

Это семь полей раннего DTO из исходника. `status`, владелец и версия конкурентного изменения не входят в первоначальное публичное представление. `photoUrl` добавляется вместе с фотографиями в 23; клиент этапа 08 не должен зависеть от него заранее.

Например, `2026-12-05T15:00:00Z` отображается в кампусе как 5 декабря, 18:00 по московскому времени. Сравнение и передача момента не должны опираться на локальный часовой пояс устройства.

## Предлагаемая обработка ошибок каталога

После переноса `ApiExceptionHandler` в 07 ошибки параметров оформляются как Spring `ProblemDetail`. Пример для некорректного `date`:

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "Некорректное значение параметра: date",
  "instance": "/api/events"
}
```

Клиент определяет результат по HTTP-статусу, использует `detail` как пояснение и имеет запасной текст, если JSON или поле недоступны. Не следует разбирать английский `title` или требовать точного текста framework-ошибки для неизвестного маршрута.

| Ситуация | Ожидаемый результат после 07 |
| --- | --- |
| Неверный формат или невозможная календарная дата | 400, сообщение о параметре `date` |
| Нечисловой ID карточки | 400, сообщение о параметре `id` |
| Неизвестная или неопубликованная карточка | 404 |
| Нет событий по фильтрам | 200, `[]` |
| Неизвестный slug категории | 200, `[]` |
| Сетевой сбой или ошибка сервера | Отдельное состояние ошибки UI; не пустая афиша |

Ошибка прав на закрытый actuator или изменяющий запрос текущего каркаса не обязана иметь тот же JSON, что будущий обработчик ошибок каталога. Это разные уровни обработки.

## Сверка перед реализацией и приёмкой

1. Дмитриев подтверждает V1 и DTO в этапе 05; при изменении модели обновляет предложенный контракт совместно с Кононовым.
2. До готовности этапа 07 три маршрута каталога остаются проектными. После реализации проверяются категории, массив событий и объект карточки.
3. Белов использует одинаковые имена полей и query-параметров, хранит фильтры в URL и отображает моменты в `Europe/Moscow`.
4. Смольянов в 09 проверяет совместные фильтры, границы суток, порядок, пустой результат, неверные параметры и отсутствие черновиков в публичном доступе.
5. Согласование и результаты фиксируются в PR и тестовом протоколе. Пока эти проверки не выполнены, документ не является свидетельством работающего API каталога.

Вход, регистрация аккаунтов, ADMIN, управление событиями и фотографии описываются на своих этапах. Запись студента на мероприятие, отмена и список участников требуют отдельной реализации и этим контрактом не объявляются готовыми.
