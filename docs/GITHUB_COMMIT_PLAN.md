# План коммитов Polyvent для GitHub на 10 рабочих дней

Подготовлен 16 ноября 2026 года по исходникам проекта, локальной истории GitLab, заданию на КП и отчёту Polyvent4. План рассчитан на пять участников с ролями из отчёта Polyvent4. Коммит 01 содержит документацию и общие настройки. В коммите 02 добавлен каркас backend на Spring Boot; следующие функциональные этапы ещё не перенесены.

Предлагаемый календарь: **16–20 и 23–27 ноября 2026 года**, понедельник–пятница. Если начало будет позже, сохранить порядок дней и сдвинуть даты. Это новый двухнедельный план; календарь первой итерации 03–16 ноября из отчёта не переносится задним числом.

## Исходное состояние и границы результата

- Источник: https://gitlab.com/aza954/polyvent. Проверенная локальная версия: `0e800308aa6c4d35bdd707d1ced1bf80d9b7841e`, ветка `main`; в ней 135 отслеживаемых файлов.
- Назначение: https://github.com/MoggBug/Polyvent. До инициализации репозиторий был пустым; основная ветка — `main`.
- Приложение: Java 21 / Spring Boot, PostgreSQL и Flyway; React / TypeScript / Vite; frontend включается в общий JAR; Docker Compose; GitLab CI и серверный контур с Caddy.
- Уже есть афиша, фильтры, карточка, вход и выход, самостоятельная регистрация аккаунта, профиль, четыре роли, администрирование пользователей, CRUD мероприятий, модерация, фотографии и автоматические тесты.
- **Пока нет записи студента на мероприятие, отмены участия, списка «Мои мероприятия» и списка участников организатора.** Регистрация аккаунта — другая функция. Эти пункты из отчёта нельзя описывать как уже перенесённые и проверенные.
- PDF задаёт требования исходного курса с GitLab CI/CD. Для текущего запроса целевой репозиторий — GitHub. Правила совместной работы и роли из главы 4 DOCX использованы как основа плана; это не поручение менять Jira, сервер или учётные записи участников.

Предлагается **31 содержательный коммит**. Основной объём — последовательный перенос существующих функций с проверками. Новая работа при переносе: GitHub Actions, документация нового процесса и фактические протоколы проверки. Полный обязательный MVP из DOCX требует отдельной реализации участия в мероприятиях после этого плана.

Это сокращения путей, не новые каталоги. Сообщения оформляются простыми русскими фразами без технических префиксов build/feat/docs. ## Порядок работы с GitHub

1. Сохранить исходную рабочую копию и всю историю GitLab. Для последовательного переноса используется отдельная рабочая копия GitHub-репозитория с собственной историей.
2. Первый организационный коммит 01 создаёт `main` в пустом репозитории. Это техническая инициализация; дальнейшая работа идёт через тематические ветки и PR. Защиту основной ветки и обязательный CI настраивать после появления ветки и рабочего workflow.
3. На задачу — отдельная ветка, например `codex/<JIRA-key>-catalog-api`. Связать требование, задачу, коммиты и PR. В сообщениях использовать реальные ключи Jira: SCRUM-7/8/9 относятся к требованиям, плану и отчёту; SCRUM-10 — потокам; SCRUM-21 — интеграции; SCRUM-22 — проверкам. SCRUM-20 не закрывать до реализации участий.
4. PR может содержать несколько коммитов, если они решают одну задачу. При объединении сохранять отдельные содержательные коммиты; squash не использовать, если требуется показать именно эту последовательность. Не создавать искусственные коммиты и не считать merge-коммиты отдельными этапами разработки.
5. Проверяющий — другой участник. Для backend: Смольянов проверяет сценарий, Белов — контракт; для UI: Смольянов проверяет поведение, Дмитриев — API; для инфраструктуры: Дмитриев проверяет сборку, Смольянов повторяет запуск; документацию Кононова сверяют владельцы модулей.
6. Автор каждого коммита соответствует фактически выполненной работе. GitHub-учётные записи и подтверждённые email остальных участников не известны и не подставлялись. Сохранённая авторизация одного пользователя не даёт основания создавать коммиты от имени всей команды.
7. В описании PR указывать происхождение кода из GitLab, реализованный этап, проверки и известные ограничения. Результаты выполнения вписывать после проверки.
